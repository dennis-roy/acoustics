# acoustics

## Microphone-only bench prototype

Test Lucas TVS starter motors and alternators using the Knowles KAS-700-0164, Raspberry Pi Pico 2 W, and Compute Module 5 on its IO Board. The mic is on hand and awaiting wiring. This roadmap covers the bench prototype. Production thresholds and component-level diagnoses require evidence from real units.

**The software handoff is ready.** Physical hardware verification remains open. Start with the [CM5 handoff](docs/cm5-handoff.md). Each numbered task has a primary file to create or extend. ### Generate offline fixtures

Run `python3 bench/simulate.py tone tone.acou` from the repository root. The script uses the standard library, checks the golden frame, and creates a new output file. Other cases are `silence`, `clipping`, `gap`, `corruption`, and `restart`. At the default rate, complete runs contain 25,600 synthetic samples. Silence and clipping are structurally complete but should exercise measurement-quality checks. Gap and corruption must invalidate the run. Restart must invalidate the incomplete first run and allow the second run to complete.

### Firmware and evaluator handoff

Build the capture library on the CM5 with `PICO_SDK_PATH` set to the existing SDK checkout. Run `cmake -S firmware -B build/pico -DPICO_BOARD=pico2_w` and `cmake --build build/pico --target acoustic_capture`. The targets `acoustic_synthetic` and `acoustic_microphone` produce USB executables and UF2 files. The Acoustic core workflow also builds the library for Pico 2 W and runs the native filter and Python evaluator checks. Inspect the run for the commit being used.

The live build requires verified header GPIOs and SELECT polarity. It runs `clk_sys` at 128 MHz and uses integer PIO divisors of 16 at 2 MHz and 10 at 3.2 MHz. The four-cycle PIO loop gives nominal 50% duty and samples in the driven half-cycle. Each run starts with 20 ms of Standard Mode clocks before switching to the Ultrasonic candidate. Inspect both rates, the transition, duty cycle, GPIO edge timing and settling on an oscilloscope. Confirm the fitted microphone and actual KAS-700-0164 electrical connections first. [Pico SDK PIO](https://github.com/raspberrypi/pico-sdk/tree/2.2.0/src/rp2_common/hardware_pio) · [Pico SDK DMA](https://github.com/raspberrypi/pico-sdk/tree/2.2.0/src/rp2_common/hardware_dma)

One 32-bit DMA word holds 32 chronological PDM samples and yields one 100 kHz PCM sample. One core owns capture and passes a private word array to `pdm_capture_read`. Drain frequently. The 8192-word ring holds 81.92 ms at the design rate. A stalled FIFO or full ring latches an integrity fault. Propagate flags to stream v1, invalidate that run and start a fresh session after recovery. Enforce a run timeout below the DMA transfer limit of roughly 44 minutes. Check status after the last read and before closing. Benchmark concurrent USB, DSP and capture, including an intentional consumer stall longer than the ring duration.

Zero-initialize the decimator for each new capture. The live firmware drops transition words and the configured Ultrasonic settling interval, then feeds 40 input words through the decimator before retaining samples. The warm-up covers FIR history. Capture timestamps still need filter delay compensation if synchronized measurements are introduced. Start transmitted sample indices at zero after warm-up. CIC3 reduces the bit rate by eight with unsigned modular arithmetic. The 129-tap FIR runs at 400 kHz and emits every fourth input. Its coefficients window an inverse-CIC passband response up to the 50 kHz design cutoff. Keep 0–40 kHz as the candidate analysis band. Independent numerical replay of the deterministic 0.30 FS reference yielded RMS-derived amplitudes of 0.3000, 0.2977, 0.2900, 0.0040, 0.0020 FS at 1, 30, 40, 65 and 360 kHz respectively. These calculations include modulation noise. Physical response, alias rejection across the band, sustained real-time throughput, and repeatability require bench measurements.

The CM5 receiver calls `bench.evaluate.evaluate` with a signed 16-bit NumPy array, validated completion state, latched status, stream source, rate, model and recipe. Results retain measured values, limits and recipe revision. Declare a transport fault even if recovered samples look plausible. The example recipe exercises synthetic limits. Valid microphone runs remain HOLD until independently validated limits exist. Suspected component is unknown pending labelled fault evidence.

### Run the integrated bench

Run `python3 -m unittest discover -s tests -p 'test_*.py'` with NumPy installed. For offline end-to-end replay, generate a fixture and run `python3 -m bench.receive --replay tone.acou --output tone-run`. Use a fresh output directory. Each run contains `audio.wav` and `result.json`. An invalid run stores its verified prefix and returns a nonzero exit status. The restart fixture records both the interrupted run and the recovered run.

Build the synthetic image with `cmake --build build/pico --target acoustic_synthetic` after configuring the SDK as above. After explicit flash approval, confirm the USB identity on the CM5 and use `python3 -m bench.receive --device DEVICE --output usb-run` with NumPy and pyserial installed. Replace DEVICE with the actual serial path. Expect 25,600 samples, 100 kHz and a synthetic PASS. Verify interruption returns INVALID, then reopen and request another run.

Configure the live build separately using `ACOUSTIC_ENABLE_MIC=ON` and explicitly supply `ACOUSTIC_CLOCK_GPIO`, `ACOUSTIC_DATA_GPIO`, `ACOUSTIC_SAMPLE_HIGH` (0 or 1) and `ACOUSTIC_SETTLE_WORDS` (100 kHz words). Verify values against the actual assembly before enabling the live board. CI uses placeholder GPIO values for compilation only. On the CM5, record sustained capture, clock and integrity results alongside the firmware revision. Live verdicts remain provisional.
